### report.md

- **The report aggregation's merge stage is no longer a `$facet`.** `$facet` materialises its whole output
  into one document capped at 100 MB; a day- or week-grouped report over a large fleet (~425 sites × 365 days
  ≈ 129k rows) overflowed it and the entire aggregation failed. It now groups per bucket and `$push`es the
  detail rows, buffering one group at a time. Subtotal accumulators gained a `__subtotal_` prefix so
  user-defined metric names can't shadow them now that both share a document. Sort behaviour is unchanged.
- **Stage 3 now carries only the site properties the final `$project` reads**, gated on `needs*` flags — every
  carried field is copied once per (site × period) bucket. `location.state` is carried instead of the whole
  location subdocument, and `blocks` is reduced at group time to three deduped string arrays.
- **The daily status report's status table is now scoped to live sites.** Disconnected sites/channels, critical
  alarms and both ticket rows count only sites in `ACTIVE_AND_LEARNING` / `ACTIVE_NOT_LEARNING`. Added a Scope
  column to the table and a business rule. (See the flag below re: Open Tasks.)

### quote.md

- **An agreed `nextRenewalDate` now wins over `today + initialSubscriptionYears`** when shipping activates a
  subscription — for single quotes and, per-child, for group quotes. The term-length calculation is now only
  the fallback. Updated the lifecycle description, the business rules, and both status-transition bullets.

### deno-ai.md

- **New: tracker alignment (`checkTracker`).** On NCU channels, compares each motor's measured angle
  (`angActual`) against its commanded setpoint (`angSet`). Detects *stuck* rows (actual range < 1° while the
  setpoint swept > 20°) and *miscalibrated* rows (mean absolute deviation ≥ 3°, critical at ≥ 15°), quotes
  estimated loss as `1 − cos(deviation)`, and emits a `good` finding when everything tracks. Detection is by
  document shape, not configuration. Documented the thresholds, the exclusion of stuck rows from the
  miscalibration list, and the domain rule that keeps wind/night stow from being read as miscalibration.
- **The current OWNER energy model now supplies block geometry.** `resolveGeometryBlocks` prefers the owner
  doc's blocks and falls back to `sites.blocks` only when there is no owner model. Correspondingly, the
  owner-model-vs-site-blocks **drift check was deleted** — with the owner model *being* the source, the two
  sides can no longer disagree. Replaced the doc's old "the site blocks *are* the energy model" claim.
- **New: how DQMS results must be reported.** The system prompt gained an explicit five-tier ranking
  (energy accounting → electrical → weather → tracker → diagnostic-only) plus a set of rules that exist to
  stop specific observed failure modes — `good` findings are passing checks not problems, proven energy
  scaling must not be re-litigated, `stat*`/`rCustom*`/`insDeno`/`irrDeno3` are off-limits for speculation,
  idle inverters read 0 legitimately but a grid-tied meter at 0 V does not.

### notification.md

- **Corrected a stale fact.** The doc said the collection is `user-notification` (singular, hyphenated).
  Commit `dc78727d` (2026-08-11) dropped the explicit `collection` option, so it is now `usernotifications`.
- **New section: the collection cutover and its migration.** Because the schema defaults `dailyStatusReport`
  to `true` and *both* the read and the write upsert, the rename didn't just hide old preferences — merely
  opening the settings page after the cutover created a fresh doc with the report **enabled**, for users whose
  last explicit choice may have been to disable it. Documented the migration's five-case merge policy, its
  asymmetric tie-break (prefer leaving someone unsubscribed over re-emailing someone who opted out), its
  idempotency, and its irreversibility.
- **New section: the Profile page.** `ProfileForm.tsx` was deleted and split into `ProfileIdentityCard`
  (read-only identity), `PersonalInfoCard` (names behind an explicit edit mode), `NotificationPreferences`,
  and `DangerZoneCard` (account deletion), over a shared `SectionCard` / `SettingRow` shell. Noted that
  account deletion is a status change to `Deleted` plus a session revoke, not a hard delete.

## Flagged for human review

1. **Open Tasks is the one daily-status row not scoped to active sites.** The commit's own comment says
   "Disconnected/Critical rows only make sense for sites that are actually live", and the disconnection, alarm
   and ticket queries all moved to `activeSiteIds` — but the Open Tasks query still uses the unfiltered
   `siteIds`. Deliberate or an oversight? The doc records the behaviour as-is either way.
   — `denowatts-backend/src/report/services/report-daily-status.service.ts:234`

2. **The user-notification migration is on `main`, but the fix it assumes is not.** The migration's merge
   policy is written around `dailyStatusReport` having been flipped to default `false` in `5284444c`
   (2026-08-19) — its comment says so explicitly. `5284444c` is on `origin/dev`, `origin/qa` and
   `origin/stage`, but **is not an ancestor of `main`**. On `main` the schema still has `default: true` and
   `getMyPreferences` (a read) still upserts with `setDefaultsOnInsert`. So running this migration against a
   `main` deployment recovers the stranded preferences and then leaves the same re-subscribe-on-page-open
   behaviour in place to re-create the problem. The portal's new `NotificationPreferences` comment —
   "visiting this page must not enable (or persist) anything" — is true on `dev`/`stage` and false on `main`.
   — `denowatts-backend/src/user-notification/schemas/user-notification.schema.ts:21-26`,
     `denowatts-backend/src/user-notification/user-notification.service.ts:14-23`,
     `denowatts-backend/migrations/20260821150000-merge-user-notification-collections.js:9-11`

3. **Still open from 2026-08-19** — the daily status report's EPI row label reads "more than 10% degradation
   from 7D average" while `countSitesWithDailyEpiExceedingWeek` counts *overperformance*. Untouched by this
